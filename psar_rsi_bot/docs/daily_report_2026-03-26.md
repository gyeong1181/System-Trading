# 데일리 리포트 2026-03-26

## 오늘 작업 요약

오늘은 이번 프로젝트를 포트폴리오 관점에서 다시 정리하는 작업을 진행했다.  
특히 단순한 봇 소개가 아니라, 실제 운영 구조와 리전 분리, Terraform 시도, 멀티 도커 운영 검토, 그리고 최종 의사결정까지 한 번에 전달할 수 있도록 시각화 아키텍처 초안을 준비했다.

핵심은 다음과 같다.

- 서울 리전은 PSAR 기반 포트폴리오용 운영 시스템
- 오리건 리전은 외부 전략용 영역으로 축소 또는 별도 운영 검토
- Terraform과 멀티 컨테이너 운영은 실제로 시도했으며, 그 제약까지 포함해 문서화
- 이번 프로젝트의 메시지를 "수익 전략"보다 "운영 가능한 자동화 시스템 구축 경험" 중심으로 다시 정리

---

## 1. 시각화 아키텍처 초안 준비

오늘은 AI 기반 시각화 제작을 염두에 두고, 프로젝트를 설명할 수 있는 Mermaid 초안을 만들었다.

구성은 두 갈래로 잡았다.

1. 현재 최종 운영 구조
- 서울 리전의 Webhook Executor
- Binance Futures
- Telegram
- CloudWatch
- Prometheus
- Grafana
- GitHub Actions
- 오리건 리전의 Terraform + Docker Compose + 외부 OKX 전략 2종

2. 이전 시도와 최종 판단 흐름
- 서울 legacy 운영
- Oregon Terraform 이전
- 멀티 컨테이너 구동 시도
- 런타임 / 인증 / 포트 / env 병목
- Binance 451 제약 확인
- 최종 역할 분리

즉, 단순 인프라 그림이 아니라 "구축 -> 시도 -> 제약 확인 -> 재설계" 흐름이 보이도록 정리했다.

---

## 2. 포트폴리오 메시지 정리

이번 프로젝트를 어떻게 보이게 할 것인지도 다시 명확히 했다.

정리한 방향:

- "이 전략으로 큰 수익을 냈다"는 식의 메시지는 지양
- 대신 실제 운영 가능한 시스템을 직접 만들고, 리전 이동과 멀티 도커 운영까지 시도했으며, 제약을 확인한 뒤 구조를 다시 설계했다는 점을 강조

즉, 이번 프로젝트의 핵심 가치는:

- Webhook 기반 자동 주문 실행기 구축
- EC2 / systemd / CI/CD 운영
- Grafana / Prometheus / CloudWatch / Telegram 관측
- Terraform apply 기반 리전 이전 시도
- Docker 멀티 컨테이너 운영 시도
- 리전 및 거래소 제약 대응
- 비용 절감 시도와 구조 재조정

추가로 오늘 기준으로 더 명확해진 점:

- 외부 vendor Docker 2종도 Render 외 환경에서 실제로 운용을 시도했다
- 다만 원 제작자 운영 흐름과 환경 적합성까지 고려하면 장기 유지 구조로는 다시 검토가 필요했다
- 따라서 이번 시도는 "구현 실패"보다 "운영 적합성 검토까지 포함한 인프라 실험"으로 정리하는 편이 정확하다

이 흐름을 포트폴리오 설명의 중심으로 두는 것이 맞다고 판단했다.

## 3. 서울 / 오리건 역할 분리 메시지 강화

오늘은 특히 서버 역할 분리 메시지를 시각화 관점에서 더 명확하게 정리했다.

### 서울 리전
- PSAR 기반 Webhook Executor
- 실거래 및 포트폴리오 증빙
- Grafana / Prometheus / CI/CD / CloudWatch / Telegram

### Oregon 리전
- Terraform 기반 인프라 실습
- 멀티 컨테이너 운영 시도
- 외부 OKX 전략 영역
- 다만 Binance Futures는 리전 제약으로 사용 불가

이 구조는 결과만 보면 "서울 유지"지만, 실제론 Oregon 이전과 구조 실험을 충분히 수행한 뒤 나온 결론이라는 점이 중요하다.
