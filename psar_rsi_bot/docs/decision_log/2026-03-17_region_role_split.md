# Decision Log | 2026-03-17 | Region and Role Split

## 결정 요약

현재 프로젝트를 아래처럼 분리 운영한다.

- 서울 리전: PSAR 기반 포트폴리오용 운영 시스템
- 오리건 리전: 탈개미AI OKX 전략 2종 전용 멀티 컨테이너 서버
- 향후 MT5 기반 신규 전략: 현재 프로젝트와 분리된 별도 트랙

---

## 1. 왜 오리건에서 우리 전략을 내렸는가

Terraform으로 Oregon 리전에 신규 EC2를 만들고, Docker Compose 기반 멀티 컨테이너 스택을 실제로 구성했다.  
이후 PSAR 컨테이너까지 함께 올려 실운영 가능성을 검증하던 중, Binance Futures API에서 `451` 응답을 확인했다.

이 문제는 코드 버그가 아니라, 리전/거래소 적합성 문제였다.

따라서 "테스트 환경이 이미 만들어졌으니 그대로 억지로 사용한다"보다, 워크로드를 리전 제약에 맞게 다시 나누는 편이 맞다고 판단했다.

결론:
- Oregon은 PSAR 실행기의 적절한 운영 리전이 아니다.
- PSAR는 서울 리전에서 유지하는 편이 맞다.
- 외부 vendor 전략 역시 Oregon에서 멀티 컨테이너 운용까지 시도했지만, 실제 운영 안정성 측면에서는 Render 환경 기준으로 더 잘 맞는 부분이 있어 유지 여부를 별도로 판단하기로 했다.

---

## 2. 왜 서울 서버를 유지하는가

서울 리전 서버는 이미 아래를 증명한 포트폴리오 자산이다.

- Webhook 기반 자동 주문 실행기 운영
- systemd 기반 상시 구동
- CloudWatch 로그 추적
- Telegram 알림
- Prometheus / Grafana 연동
- GitHub Actions 기반 배포

즉, 서울 서버는 단순한 "옛날 서버"가 아니라, 현재 프로젝트의 운영 증빙이 가장 잘 남아 있는 환경이다.

따라서 서울 서버는 전략 수익성보다 **운영 가능한 시스템을 직접 만들고 돌린 경험**을 보여주는 용도로 유지하는 것이 맞다.

---

## 3. 왜 현재 전략을 포트폴리오용으로 격하했는가

현재 PSAR 기반 전략은 실제로 운영 가능한 시스템을 검증하는 데에는 충분한 가치가 있다.  
하지만 장기적으로 핵심 수익 전략으로 밀어붙일 정도의 확신은 높지 않다.

따라서 이 전략의 위치를 다음처럼 다시 정의했다.

- 이전: 실전 핵심 수익 전략 후보
- 현재: 포트폴리오용 운영 증명 자산

이렇게 정리하면 메시지가 더 명확해진다.

- 과장 없이 말할 수 있다.
- 실제로 구축하고 운영한 시스템이라는 강점은 유지된다.
- 향후 더 나은 전략을 별도 트랙에서 준비할 수 있다.

---

## 4. 왜 MT5 프로젝트를 별도로 분리하는가

향후 계획 중인 MT5 기반 멀티 전략 프로젝트는 현재 저장소와 목적이 다르다.

현재 저장소의 목적:
- 운영형 자동화 시스템
- 배포 / 관측 / 알림 / 인프라 이전 / 문서화 경험

향후 MT5 저장소의 목적:
- 신규 전략 연구
- 멀티 전략 파이프라인
- 더 직접적인 실전 수익 구조

둘을 한 저장소에 섞으면 다음 문제가 생긴다.

- 포트폴리오 메시지가 흐려진다.
- 운영 시스템과 전략 연구 코드가 뒤섞인다.
- 문서와 배포 경로가 복잡해진다.

따라서 MT5 프로젝트는 별도 저장소, 별도 서버 구조로 분리하는 것이 맞다.

---

## 5. 비용 관점 판단

과거에는 Render에서 컨테이너를 분산 운영하며 월 약 21,000원 수준의 비용이 발생했다.  
이를 줄이기 위해 외부 전략 2개를 AWS 단일 인스턴스에 묶는 방향을 시도했다.

이 시도는 유효했다.  
다만 비용 절감만을 기준으로 모든 워크로드를 한 서버에 밀어 넣는 것이 항상 정답은 아니었다.

결론적으로:
- 비용 절감 시도는 계속 유지
- 하지만 거래소/리전 적합성이 더 중요할 때는 역할 분리 우선

즉, 이번 결정은 비용과 운영 적합성 사이에서 균형을 다시 맞춘 결과다.

---

## 6. 이번 시도를 어떻게 설명할 것인가

이번 과정은 "이전 실패"로만 설명할 필요가 없다.

더 정확한 설명은 다음과 같다.

- Terraform으로 신규 리전을 직접 만들었다
- 멀티 컨테이너 구조를 실제로 구성하고 구동을 시도했다
- 외부 vendor 컨테이너를 Render 외 환경으로 옮겨 운영 적합성을 검토했다
- Binance 리전 제약과 vendor 환경 적합성을 확인한 뒤, 최종 운영 구조를 다시 조정했다

즉, 실행까지 직접 해보고 제약을 확인한 뒤 의사결정을 내렸다는 점이 핵심이다.

이 문서를 면접이나 포트폴리오 설명에서 사용할 때는 다음 표현이 적절하다.

- "리전 이전을 직접 시도했다"
- "멀티 컨테이너 운영을 실제로 검증했다"
- "제약을 확인하고 구조를 재설계했다"

반대로 아래처럼 말할 필요는 없다.

- "완전 이전에 성공했다"
- "모든 외부 전략을 안정적으로 이관했다"
