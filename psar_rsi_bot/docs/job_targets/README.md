# Job Targets | 프로젝트 설명 포인트

이 디렉터리는 특정 채용 포지션에 맞춰 이 프로젝트를 어떻게 설명할지 정리하는 공간입니다.

현재 이 프로젝트는 아래 관점에서 설명하는 것이 가장 적절합니다.

---

## 한 줄 요약

Webhook 기반 자동 주문 실행기를 직접 구축하고, AWS EC2 / systemd / Docker / CI/CD / Prometheus / Grafana / Terraform / 리전 제약 대응까지 실제로 운영하며 구조를 분리한 포트폴리오형 운영 시스템.

---

## 클라우드 엔지니어 / 인프라 엔지니어 관점

어필 포인트:

- AWS EC2 기반 운영 경험
- Security Group, SSH 허용 CIDR, 리전별 인프라 구성 경험
- Terraform `plan` / `apply` 기준 신규 리전 인프라 생성 경험
- SSM Parameter Store 기반 secret 관리 경험
- 리전 제약과 거래소 적합성을 확인한 뒤 워크로드를 재배치한 경험

면접에서 강조할 문장:

"단순히 서버를 한 대 띄운 것이 아니라, 서울과 오리건 리전의 역할을 다르게 두고, 거래소 제약과 운영 목적에 맞게 시스템을 분리했습니다."

---

## DevOps 관점

어필 포인트:

- GitHub Actions 기반 배포
- systemd 기반 서비스 운영
- Docker Compose 멀티 컨테이너 운용
- GHCR private image pull 및 레지스트리 인증 문제 추적
- 운영 체크리스트와 결정 로그 문서화

면접에서 강조할 문장:

"배포 자동화와 런타임 운영을 분리해서 봤고, 실패 원인을 코드, 인프라, 레지스트리 인증, 포트 매핑, 리전 제약으로 나눠 추적했습니다."

---

## 관측 / 운영 관점

어필 포인트:

- Prometheus `/metrics` 수집
- Grafana 대시보드 / 알림 룰 구성
- Telegram 알림 연계
- CloudWatch 로그 추적
- 운영 로그 기반 트러블슈팅

면접에서 강조할 문장:

"서비스가 살아 있다는 것만 본 게 아니라, 메트릭, 알림, 로그를 함께 보면서 운영 가능한 상태를 확인했습니다."

---

## 비용 / 운영 효율 관점

어필 포인트:

- Render에서 전략별 분산 운영 시 월 약 21,000원 수준의 비용 구조를 경험
- 이를 줄이기 위해 AWS 단일 인스턴스 멀티 컨테이너 구조를 시도
- 단, 비용 절감만 우선하지 않고 거래소/리전 제약까지 고려해 최종적으로 서버 역할을 분리

면접에서 강조할 문장:

"비용 절감을 위해 통합을 시도했지만, 실제 제약을 확인한 뒤에는 운영 적합성을 기준으로 다시 분리하는 판단을 했습니다."

---

## 현재 프로젝트를 가장 잘 설명하는 포지셔닝

이 프로젝트는 다음처럼 설명하는 것이 가장 적절합니다.

- 수익률 자랑용 전략 프로젝트
- 단순 봇 제작 프로젝트

보다는

- 운영 가능한 자동화 시스템을 직접 구축·배포·관측·분리 운영한 경험을 담은 프로젝트

전략 성능보다 **운영형 시스템 구축과 의사결정 경험**을 중심으로 설명하는 것이 맞습니다.
